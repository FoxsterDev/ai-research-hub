# Техдок по Figma: как мы генерируем Design Tech Doc и ассеты — полевой отчёт

Дата: 2026-08-20 · язык: русский · аудитория: внешняя (командам, которые делают UI-контент из Figma для Unity)

Документ самодостаточный: чтобы его прочитать, доступ к нашим репозиториям не нужен. Конкретные имена проектов, файлов дизайна, нод, бакетов и меню намеренно обобщены — все механики, гейты и грабли описаны полностью.

---

## TL;DR

- «Техдок по фигме» у нас — это не описательный документ, а **исполняемый контракт партии макетов**: Design Tech Doc (DTD). Из его секций буквально запускаются экспорт арта и генерация Unity-ассетов.
- Пайплайн из 7 стадий с явными гейтами. Один гейт — **блокирующий и человеческий**: решение, какие тексты запекаются в пиксели, а какие приходят с сервера.
- Замер на живом батче: **~5 минут агентской работы на попап**, 6 готовых скинов за один проход. От человека нужны ровно две вещи: утверждение текстовой политики и клик на публикацию.
- Главный урок, оплаченный отдельным провалом: **«скомпилировалось + сценарий прошёл + скриншот снят» ≠ «макет реализован»**. Визуальная приёмка — отдельная полоса с честными терминальными статусами.

---

## 1. Задача

Дизайнер публикует в Figma UI-референсы (попапы, баннеры, скины). Инженерной стороне нужно:

1. пройти по файлу и выбрать **только те фреймы**, которые ложатся на поддерживаемый рантайм-контракт контента (не каждый фрейм — шипабельный контент);
2. вытащить выбранные фреймы в ревьюибельный техдок (id нод, таблица экспорта, параметры лэйаута, политика текстов);
3. экспортировать пиксель-точный арт в целевых размерах контракта;
4. сгенерировать из техдока Unity-ассеты (папки, спрайты, атласы, конфиг-ScriptableObject) через Editor API — **никогда** правкой YAML;
5. опубликовать существующей контент-полосой проекта;
6. сверить отрендеренный результат с референсом из Figma.

Ключевое отличие от «агент посмотрел макет и что-то сделал»: каждая стадия оставляет артефакт, который можно перечитать, отревьюить и перезапустить.

## 2. Два слоя

Разделение принципиальное, оно же делает пайплайн переносимым:

| Слой | Что содержит | Чего в нём быть не должно |
|---|---|---|
| **Движок** (публичный, host-agnostic) | стадии и гейты, контракт DTD, шаблон техдока, generic-тулинг экспорта по Figma REST | имён игр, ключей файлов, id нод, размеров конкретного контракта, инфраструктурных имён |
| **Host-оверлей** (приватный, на стороне проекта) | какой файл дизайна → какой контракт контента, размеры ролей, схема ассетов, точка входа генератора, полоса паблиша, полоса валидации | — |

Практический эффект: размеры и viewport — это **конфиг**, а не константы в коде тулов. Публичный экспортер получает `--config host_config.json` и резолвит `role` (`card_art` / `cta_button` / `close_icon`) в целевые пиксели оттуда.

## 3. Полосы доступа к Figma

Берётся первая доступная; они дополняют друг друга, а не исключают.

| Полоса | Для чего | Требования | Заметки |
|---|---|---|---|
| **Figma REST API** (свой скрипт) | детерминированный листинг дерева нод и пиксель-точный PNG-экспорт с вычисленным масштабом | personal access token в переменной окружения | **основа пайплайна** |
| **Remote Figma MCP** | разговорный просмотр файла, метаданные ноды, выбор фреймов | любой план и тип сита, OAuth в браузере | ссылочный: кидаешь URL — сервер резолвит ноду |
| **Desktop Figma MCP** | то же, но по текущему выделению в приложении | Dev/Full сит на платном плане, запущенное десктоп-приложение | только если remote недоступен или запрещён политикой |
| **Скриншот браузера** | глазами найти нужную секцию | залогиненная сессия | **никогда** как источник спрайтов: не тот масштаб, нет прозрачности, хром канваса |

Токен читается из переменной окружения (или из файла вне репозитория с правами `600`), никогда не передаётся аргументом CLI и не попадает в репозиторий, техдоки и отчёты. Скоупа «File content → read-only» достаточно: используются только `/v1/files` и `/v1/images`.

## 4. Пайплайн

```
S1 Select → S2 Extract → S3 Design Tech Doc → S3a Text-policy approval (блокирующий)
S4 Export → S5 Generate → S6 Publish → S7 Visual Acceptance
```

**S1 Select.** Перечисляем секции/фреймы файла и классифицируем каждый против контрактов контента. Дальше идут только контракт-совместимые; всё остальное **явно перечислено** как `out_of_scope` с причиной (`not_contract_shaped`, `different_runtime_surface`, `duplicate`). Выборка — подтверждаемый человеком артефакт, а не неявный фильтр в голове агента.

**S2 Extract.** Для каждого выбранного фрейма читаем дерево нод и находим роли контракта (арт карточки, CTA-кнопка, иконка закрытия, текстовые ноды). Записываем id нод, натуральные размеры, позиции в системе координат фрейма, при необходимости заливки и типографику.

**S3 Design Tech Doc.** Один документ на батч по шаблону. Это единственный источник правды для всего, что идёт дальше.

**S3a Text-policy approval — блокирующий гейт.** См. §6.

**S4 Export.** Экспортер получает таблицу экспорта из техдока, вычисляет масштаб Figma по целевому размеру для каждой ноды и **проверяет размеры полученного PNG**. Несовпадение — фейл стадии; арт никогда не ресайзится молча.

**S5 Generate.** Драйвим генератор на стороне проекта (меню-тул, статический API или программный хук). Генерация идёт через Unity Editor API (импортеры, SpriteAtlas API, `SerializedObject`); авторинг YAML запрещён. Генератор **клонирует** настройки импортера/атласа/конфига с объявленного шаблонного ассета — так дрейф контракта невозможен.

**S6 Publish.** Существующая контент-полоса проекта ровно в том виде, в каком её проходит человек. Пайплайн не заводит параллельный путь публикации.

**S7 Visual Acceptance.** Регистрируем экспортированный арт как визуальный референс и сравниваем с рендером. См. §8.

### Гейты стадий

- S1 обязан назвать **каждый** пропущенный фрейм с причиной.
- S3a должен быть явно утверждён до S4: неутверждённая политика текстов блокирует **генерацию**, а не только публикацию.
- S4 падает, если размеры любого PNG отличаются от целевых.
- S5 падает, если генератор репортит предупреждение контракта, которое техдок явно не отменил.
- S7 не выдаёт вердикт без детерминированного состояния; `blocked_nondeterministic` и `pending_manual_style` — честные терминальные состояния.

## 5. Что внутри Design Tech Doc

Скелет (по одному документу на батч):

```markdown
# Design Tech Doc — <имя батча>
Status: draft | approved | exported | generated | published | accepted
Source file: <ключ файла> · Selected by: <кто подтвердил выборку> · Date: <YYYY-MM-DD>

## 1. Selection record (S1)
| Frame | Node id | Section | Verdict | Reason |
— каждый фрейм просмотренных секций ровно один раз, без неявных скипов

## 2. Per-item extraction (S2)
- контракт контента, рантайм-id
- role mapping: роль | node id | имя ноды | натуральный размер | целевой размер | масштаб
- параметры лэйаута с ЯВНЫМ выводом (как позиция в координатах фрейма превращается
  в поле конфига)
- таблица политики текстов (S3a): нода | контент | вердикт | слот/серверное поле |
  прямоугольник из геометрии ноды | required | обоснование
- блокеры, список нод, исключаемых из арта, запись об утверждении
- маски/вариативность для приёмки, открытые вопросы к дизайнеру

## 3. Export table (S4)  ← машиночитаемая, скармливается экспортеру как есть
## 4. Generation parameters (S5)  ← поля генератора + шаблонный ассет-донор
## 5. Publish record (S6)
## 6. Acceptance record (S7)  ← вердикт + ссылки на expected/actual/overlay/diff
```

Секция 3 — не иллюстрация, а буквально спека:

```json
{
  "file_key": "<ключ файла>",
  "out_dir": "<staging-директория вне Assets/>",
  "items": [
    { "item": "MySkin",
      "exports": [
        { "node_id": "<группа карточки>", "file": "MySkin/Popup.png", "role": "card_art",
          "exclude": ["<иконка закрытия>", "<CTA, если внутри карточки>", "<конфигурируемые тексты>"] },
        { "node_id": "<CTA>",   "file": "MySkin/ButtonCTA.png",  "role": "cta_button" },
        { "node_id": "<крестик>", "file": "MySkin/Icon Close.png", "role": "close_icon" }
      ] }
  ]
}
```

Два свойства, ради которых всё это писалось: техдок **ревьюится человеком до траты денег на экспорт и генерацию** и **перезапускается** без переоткрытия Figma.

## 6. Текстовая политика — самый дорогой выбор в пайплайне

У любого текста в макете три возможных дома:

| Вердикт | Когда | Где живёт |
|---|---|---|
| **bake** (запечь в арт) | статичная копия, не зависящая от юзера, страны, эксперимента и математики наград: заголовки, слоганы, юридические подписи; плюс всё, чью типографику (градиент, обводка, кастомный кернинг) текстовый компонент не воспроизведёт | внутри экспортированного PNG |
| **configure** (серверный слот) | значение, зависящее от юзера/сегмента/кампании, или то, что продукт захочет менять без релиза клиента: суммы наград, призовые пулы, счётчики, таймеры, названия кампаний, A/B-копия | слот рантайм-конфига + запись в конфиг-ассете |
| **dynamic** (считается на клиенте) | производное от живого состояния клиента (остаток времени, текущий баланс) | этой поверхностью **не поддерживается** — нужен отдельный вью, не надо имитировать слотом |

Правила, которые делают гейт блокирующим:

- **Цена ошибки необратима.** Выбор определяет одновременно запечённые пиксели **и** контракт серверных данных. Передумать позже = переэкспорт арта + пересборка и переналивка бандла.
- Агент **предлагает**, человек **утверждает**. Дефолт для всего, что варьируется — `configure`.
- Конфигурируемый текст обязан быть **исключён из экспортируемого арта**, иначе значение нарисуется дважды: один раз запечённым, второй раз рантаймом.
- Декоративные соседи (иконка монеты, символ валюты) при этом **остаются запечёнными** — исключается только меняющаяся строка.
- Геометрия исключённой ноды становится прямоугольником слота: позиция = центр ноды минус центр карточки (y инвертируется), размер = размер ноды, выравнивание — по дизайну.
- Блокеры называются явно: конфигурируемых текстов больше, чем вью умеет отрисовать; типографику текстовый компонент не повторит; текст вварен дизайнером в арт карточки (нужно, чтобы дизайнер разделил слои — **никогда** кроп скриншотом).

До утверждения батч имеет статус `text_policy=pending_approval` и не может быть ни сгенерирован, ни опубликован.

## 7. Экспорт: что делает тулинг

- **Масштаб не задаётся руками.** Порядок разрешения размера: явный `scale` → явные `target_width`/`target_height` → размер по роли из host-конфига. Масштаб считается из натуральных границ ноды.
- **Проверка аспекта.** Если ширина требует одного масштаба, а высота — другого с расхождением больше 2%, стадия падает с явным сообщением: чинить надо целевой размер или ноду в Figma, а не «примерно подогнать».
- **Потолок Figma — масштаб 4.** Цель, требующая большего, фейлится явно, а не тихо отдаёт мыло.
- **Композитный экспорт.** `"exclude": [id, ...]` реализован не «вырезанием»: экспортер перерендеривает **видимые листовые части** ноды с выброшенными исключёнными поддеревьями и сшивает их на прозрачном канвасе по координатам. `bounds_node_id` нужен, когда части живут вне целевой ноды (например, оверлей на уровне фрейма должен попасть в кроп карточки) — тогда геометрия и кроп берутся от указанной ноды.
- Staging-выход — во временную папку вне `Assets/`, ассеты появляются в проекте только на стадии генерации.

## 8. Визуальная приёмка — и главный урок

Отдельная сессия, с которой всё началось, выглядела так: дан референс 1440×3200, проект компилируется, play-mode проходит, сервисные вызовы в логах есть, скриншот снят, сценарий зелёный. Результат визуально **не совпадал** с макетом: другая пропорция карточки, не отрисованный body-текст, пустая область в лэйауте. Плюс всплыл реальный дефект — у кнопки закрытия был устаревший GUID скрипта, компонент не резолвился и презентер падал на подписке. Компиляция этого не ловит в принципе.

Вывод, зафиксированный в ретро:

```
compile passed + runtime passed + screenshot captured
≠
reference accepted
```

Что из этого выросло:

- **Референс — это контролируемый тестовый вход, а не вложение в промпт.** У него манифест: неизменяемая картинка + хеш, viewport/ориентация/safe-area, состояние продукта, которое надо отрендерить, обязательные тексты, сравниваемые регионы с весами, объявленные маски, пороги и владелец осознанного отклонения.
- **Приёмка — не пиксельное равенство.** Разрешение Game View переключаемое и будет отличаться от референса; сравнивается человеко-видимое сходство (цвет, детали, положение, размер) на resolution-independent сетке с объявленными допусками. Несовпадение viewport/ориентации должно давать `comparison_not_comparable`, а не красивый бессмысленный процент.
- **Маска — ревьюибельный артефакт.** Маскировать таймер или рекламную область можно только по объявлению в манифесте; маска на всю карточку — провал политики, а не пройденный тест.
- **Три вида доказательств не заменяют друг друга.** Визуальный скор не доказывает, что кнопка кликабельна. Семантическое дерево (текст на месте, RectTransform верный) не доказывает отсутствие клиппинга, неверного порядка отрисовки или не того спрайта. Присутствие кнопки на скриншоте не доказывает, что нажатие работает.
- **Недетерминированное состояние — не «почти прошло».** Если экран зависит от живых серверных данных, таймера, локали или готовности рекламы и это не зафиксировано фикстурой, вердикт — `blocked_nondeterministic`.
- **Ручная стилизация — это состояние передачи, а не успех.** Когда дизайнер/разработчик забирает шрифты и отступы себе, статус — `pending_manual_style` с перечислением оставшихся регионов. Он никогда не повышается до «принято» на основании зелёной компиляции.

Быстрая полоса итерации, без которой всё это неприменимо: **изолированный рендер префаба/канваса** в целевом viewport за секунды, вместо полного буста приложения на каждую правку лэйаута. Полный play-mode остаётся нужен для поведения, но не для каждого сдвига на 10 пикселей.

## 9. Результаты

Замеры на реальном батче (один рабочий проход, 6 попапов):

| Шаг | Кто | Время |
|---|---|---|
| Инспекция фрейма, список нод карточки/CTA/крестика/текстов | агент | ~1 мин |
| **Предложение текстовой политики и ожидание утверждения** | агент → **человек** | ~1 мин + ревью |
| Экспорт арта в точных размерах, проверка размеров, взгляд глазами на карточку | агент | ~1 мин |
| Генерация папки скина (спрайты, атлас, конфиг-ассет, слоты) | агент | ~1 мин |
| Проверка guid'ов / атласа / слотов | агент | ~1 мин |
| Сборка и заливка в dev-окружение | человек | ~2–5 мин |
| Визуальное сравнение с референсом | агент | ~2–5 мин |

Итого **~5 минут агентской работы на попап**. Батч из 4–6 однотипных попапов стоит примерно столько же, потому что экспорт и генерация — поцикловые.

Фактические цифры прохода: 6 скинов (4 полностью запечённых, 2 с серверным слотом на сумму), экспорт — ноль расхождений по размерам, генерация — все запуски успешны с нулём предупреждений, компиляция после генерации — 0 ошибок. Публикация и визуальная приёмка на момент закрытия техдока стояли как `pending` — и так и записаны, а не закрашены зелёным.

Что реально требует человека: **одно решение по текстам на попап** и **клик на публикацию**. Всё остальное механическое.

Что идёт медленнее: макет, где CTA или сумма вварены в арт карточки (нужен дизайнер, чтобы разделить слои); попап, которому нужно больше динамических текстов, чем умеет вью (это правка клиента и релиз, а не бандл); новое семейство попапов с размерами, которых нет в host-конфиге (одна новая запись контракта).

## 10. Подводные камни — все оплаченные

### Продуктовые и контрактные

- **Текстовая политика необратима.** В нашем же батче один попап сгенерировали с запечённой суммой — пришлось переэкспортировать карточку с исключённой нодой и перегенерировать скин. Именно поэтому S3a стал блокирующим гейтом, а не рекомендацией.
- **Слотов в данных больше, чем умеет отрисовать вью.** У нас в данные сериализуется 8 слотов, а префаб биндит **два**. Слот с индексом ≥ 2 объявляется без ошибок и **молча не рендерится**.
- **И один путь не молчит.** Слот, помеченный `required`, презентер проверяет по серверным данным: если строки нет — он логирует ошибку и **скрывает весь попап**, не заглядывая в биндинги префаба. Итог: `required`-слот без биндинга — живой прод-хазард. Это невозможно вывести из макета, поэтому у нас отдельный документ-владелец с якорями в исходники.
- **Требуемый слот без данных для сегмента = попап не покажется этому сегменту.** Хэндофф админу (какой id дизайна, какие поля заполнить, для каких сегментов) — обязательная часть техдока.

### Экспортные

- **CTA бывает то сиблингом карточки, то внутри неё** — в разных секциях файла по-разному. Во втором случае его нужно явно исключить, иначе кнопка запечётся в арт и нарисуется дважды.
- **Композитный экспорт может сдвинуть пиксели.** Если у листовой части есть эффекты и её рендер на пару пикселей больше её же границ, сшиватель перецентрирует часть. Проверка размеров этого не ловит — **обязательно посмотреть на итоговый PNG глазами**. Тот же взгляд ловит забытый оверлей и всё ещё запечённое значение.
- **Оверлей вне карточки** (иконка на уровне фрейма поверх карточки) требует `bounds_node_id` **плюс** исключения фона-мокапа, на котором карточка лежит в макете.
- **Валидный токен на аккаунте без доступа к файлу возвращает 404**, а не 403. Классическая потеря получаса при онбординге нового человека: сначала проверяем доступ к файлу, потом токен.
- Потолок масштаба 4 и проверка аспекта — не раздражители, а именно то, что не даёт получить «вроде похожий» арт.

### Unity-сторона

- **Guid'ы проверять пофайлово.** Один раз позиционное сопоставление вывода grep по нескольким `.meta` дало неверную привязку префаба. Теперь только по одному файлу за вызов.
- **Расположение папки `Editor/` имеет значение.** Наш сборщик бандлов включает содержимое любой папки, подходящей под маску имени, и пропускает только несовпадающие папки **верхнего уровня** — редакторный код рядом с контентом должен лежать сиблингом, а не внутри.
- **Имена папок становятся сегментами ключа в хранилище** — только буквы и цифры, регистр фиксирован. Это не косметика, а требование сборщика.
- **Генератор репортит предупреждения, но не падает на них** — верификация после генерации (guid'ы указывают в свою папку, атлас включён в билд, оверрайды слотов соответствуют утверждённой политике) обязательна.
- **Спрайт-режим наследуется от шаблона-донора.** Донор в режиме `Multiple` даёт именованный саб-спрайт с нестандартным fileID в конфиге — это корректно, пока guid указывает на файл своей папки. Знать это заранее дешевле, чем расследовать.

### Процессные

- **Никакого «pixel perfect» без объявленного окружения рендера.** Растеризация шрифтов, device scale, динамический контент и системные safe-area требуют объявленных порогов и масок — иначе честный ответ инструмента «сравнивать нельзя».
- **Зелёный сценарий не повышается до визуальной приёмки** ни при каких обстоятельствах. Отчёт закрывается таблицей из трёх полос (техническая / функциональная / визуальная), каждая со своим допустимым доказательством.

## 11. Минимальный набор, если повторять у себя

По убыванию отдачи:

1. **Шаблон техдока как исполняемый контракт** — с машиночитаемой таблицей экспорта внутри. Даже без всякой автоматизации это убирает главный класс потерь: «непонятно, откуда взялась эта цифра в конфиге».
2. **Конфиг host-контракта** (viewport + размеры по ролям) вместо констант в тулах. Разделение «движок / оверлей» окупается на втором проекте.
3. **Блокирующий гейт по текстовой политике.** Это единственное место, где человек обязан быть, и единственное, где ошибка стоит переэкспорта и переналивки.
4. **Экспорт с проверкой размеров** и явными фейлами вместо тихой подгонки.
5. **Генерация только через Editor API** с клонированием шаблонного ассета.
6. **Отдельная визуальная полоса** с честными терминальными статусами. Даже в самом дешёвом виде — side-by-side референса и захвата в том же viewport с явной подписью владельца.

## 12. Чего пайплайн не делает

Чтобы не было завышенных ожиданий:

- не заменяет дизайнера: вваренный в арт текст, недостижимая типографика и «сделай красиво» уходят человеку;
- не изобретает контракт контента — он должен уже существовать в рантайме, пайплайн только ложится на него;
- не публикует в прод сам: продовая заливка остаётся отдельным человеческим решением;
- не выдаёт вердикт по недетерминированному экрану — вместо этого говорит, что состояние не зафиксировано.
